# データ取得の仕組み

[English](DATA_ACQUISITION.en.md) · [文書の目次](README.md)

NenRingが何を、どこから、どうやって取得しているかをまとめた文書です。取得から寿命予測までの流れと、同じ情報をターミナルで確認するためのコマンドも掲載しています。予測の読み方は [FORECAST_GUIDE.md](FORECAST_GUIDE.md) を、計算の中身は [NAND_MODEL_V2_4.md](NAND_MODEL_V2_4.md) を参照してください。

NenRingが取得するのは次の情報です。統計の取得ではSSDの設定やfirmwareを変更しません。履歴や設定のファイル保存は行います。

| 情報 | 取得元 | 既定の間隔 | 権限 |
|---|---|---|---|
| SMART | `smartctl`（smartmontools） | 10分 | 通常のユーザー |
| NANDの構成 | IORegistry（公開IOKit API。ターミナルでは`ioreg`） | 1日（ライフサイクルや取得可否に応じた更新あり） | 通常のユーザー |
| FTLの統計（Direct FTL） | Appleの非公開インターフェース（同梱のprobe） | 10分（SMARTと同じ周期） | 通常のユーザー（手動の再試行のみ管理者認証を求めることがある） |
| リアルタイムI/O | IOBlockStorageDriverの累積バイト数 | バックグラウンド監視中は既定2秒 | 通常のユーザー |

## SMART

SMART全体の取得間隔は5・10・15・30分、1時間から選択でき、既定は10分です。以前の範囲外の保存設定は現在選択できる範囲へ読み替えます。温度は独立した周期で記録し、その更新では現在温度と温度グラフのみを更新します。境界検査・損耗・WAF・保持推計・イベント解析は、SMART／FTL／IORegistry／設定等の全体入力更新時に行います。温度履歴は破棄せず、次回の全体解析へ渡します。全体解析中に温度が更新された場合も、古い解析結果で新しい温度グラフを戻さないようにしています。

「ディスク情報」画面ではSMARTとIORegistryの保存済み情報を、取得元ごとの時刻付きで確認できます。画面を開くのみでは新たな取得を行いません。SMART JSONは識別情報を含む場合があり、共有前に除く必要があります。IORegistry全文は保存せず、解析済みの構成情報を表示します。

SMARTの自動取得が失敗した場合は、メイン画面とメニューバーに取得失敗を表示します。最後に成功した値は残し、案内には最終成功時刻を添えます。自動取得中に表示を「確認中」へ切り替えることはせず、次の取得に成功した時点で失敗表示を解除します。温度のみの取得成功ではSMART全体の失敗表示を解除しません。

SMART（S.M.A.R.T.、Self-Monitoring, Analysis and Reporting Technology）は、SSDやHDDが自身の状態を報告する仕組みです。NVMeでは「SMART / Health Information」というログとして定められています。smartmontoolsは必須で、アプリには同梱していません。NenRingは、利用者がインストールした `smartctl` を別のプログラムとして実行し、その出力（JSON）を読み取ります。

使用している主な項目はPercentage Used、Data Units Written・Read（1単位は512,000バイト）、Power On Hours、Power Cycles、Unsafe Shutdowns、温度、Available Spare、Critical Warningです。

### 内蔵SSDの選び方

1. `smartctl --scan-open -j` で、SMARTを取得できる機器の候補を収集します。
2. 各候補を `diskutil info -plist` で確認し、macOSが内蔵（`Internal`）と判定したものを優先します。
3. 選択した機器から `smartctl -j -i -H -A -c` で値を取得します。`-c`は同じIdentify情報から対応機能を表示する指定です。温度のみを取得する場合は、前回選択した機器に `smartctl -j -i -A` を実行します。`-i` で読んだシリアル番号などが前回と同じかを確認し、異なる場合は再選択します。
4. 温度を記録するときは、同じ機器の IOBlockStorageDriver の `Statistics` から、読み込み・書き込みバイト数（`Bytes (Read)`・`Bytes (Write)`）も取得します。選択したSMART機器に対応するドライバを検索し、1つに特定できなければ記録しません。ドライバ単位の累積値のため、再起動に加えてドライバの再生成でも区切られます。起動時刻（`kern.boottime`）と、取得できたdriver IDを一緒に保存します。SMARTの取得間隔とは別に低負荷区間を判断するための記録であり、SMARTの生涯累積値の代わりには使用しません。

### ターミナルでの確認

```bash
smartctl --scan-open -j
```

```bash
smartctl -j -i -H -A -c /dev/disk0
```

```bash
diskutil info -plist /dev/disk0
```

`/dev/disk0` は内蔵SSDのことが多いですが、Macによって異なることがあります。1つ目のコマンドの結果で確認してください。

### 追加統計と機能情報

同じSMARTログのHost Read／Write Commands、Controller Busy Time（分）、Error Information Log Entriesを任意項目（Optional）として保存します。「ディスク情報」で累積値と、同じdevice・firmwareの直前のSMART取得からの増分を確認できます。時刻重複・稼働時間逆行・firmware変更では比較を保留し、個別counterの逆行はその項目のみ保留します。取得できない値を0にせず、古い履歴へ追加値を補完しません。

平均要求サイズは同一区間のData Unitsの差分×512,000÷コマンド数の差分です。分母が0の場合やcounterが逆行した場合は表示しません。この値はアクセスのランダム／逐次を判定するものではありません。Busy Timeが0であっても、実際に負荷がなかった証明とは扱いません。

NVMeの機能ビットは機器が報告する対応情報です。TRIM／Deallocate対応は実行履歴ではなく、self-test対応もmacOSから実行できる証拠ではありません。IORegistry側では選択したSMARTサービスの`IOStorageFeatures.Unmap`を、日次等の既存のIORegistry取得時に読み取ります。別ディスクの値やNVMe機能ビットで補完しません。

`-a`／`-x`／`-l error`／`-l selftest`による詳細ログの定期取得は行いません。取得できないログを繰り返し問い合わせることはせず、画面には「未取得（定期取得なし）」と表示します。通常SMARTのエラーログ件数はその詳細ログとは別です。TRIM・self-test・firmware操作の実行機能は追加しません。

## リアルタイムI/O

バックグラウンド監視中にSMART対象が選択されていれば、そのIOBlockStorageDriverの`Statistics`のみを1・2・5秒間隔（既定2秒）で取得します。設定の「メニューバーにI/O速度を表示」はアイコン横の速度文字列のみを切り替え、取得自体は停止しません。メニューバーには読込・書込の片方／両方、または速度非表示を選択できます。ポップアップは左に現在速度、右に直近5分のグラフを表示します。中央線より上の赤が書込、下の青が読込で、共通の速度スケールを使用します。両者は加算せず、下向きの描画も負のI/O量を意味しません。グラフの下に「書込の詳細」と「短期集計」が並び、累積量と観測秒数も表示されます。

「書込の詳細（直近30秒）」には対象SSDのブロック書込速度と、Mac全体で観測した書込プロセス上位3件を表示します。順位は直近30秒の観測区間で平均し、短い書込も一定時間残ります。スワップアウトはページ数を実行環境のページサイズでバイト換算した平均速度です。圧縮後のSSD書込量やプロセスごとの書込先は特定できません。

速度は累積カウンタの差分÷単調時計の実経過時間です。ドライバはキャッシュし、対象の変更時と取得失敗時に再解決します。新しい温度記録にもOptionalのregistry driver IDを保存します。driver ID・起動時刻の変更、counter逆行、取得失敗、取得間隔の3倍を超える欠落では差分を連結せず、比較待ちに戻します。スリープ中とバックグラウンド監視の停止中は取得せず、復帰後もその区間を補間しません。

直近5分のサンプルはメモリ内の最大301区間のみです。窓の境界のみ時間按分し、実観測秒数を併記します。監視中の累積も有効区間の合計のため、停止中・欠測中のI/Oは含みません。アプリの再起動と対象の変更で消去し、ディスクには保存しません。高頻度更新は専用の表示モデルのみへ通知し、SMART・FTL・保持解析・寿命予測の再計算を起動しません。

これはOSのブロックI/O統計で、SMARTの生涯Host量やFTLのNAND量とは定義が異なります。それらへ加算したり、WAFや保持温度の学習入力へ自動投入したりしません。低負荷温度の判定への利用は別途検証する段階です。

## IORegistry（NANDの構成）

取得に成功した構成情報はその起動中の取得先にひも付けてキャッシュします。通常のSMART更新では同じ取得先のキャッシュを再利用し、追加のioreg取得は行いません。対応付けが一時的に失われた場合は構成情報の使用を保留し、同じ取得先へ戻れば次のSMART更新で復元します。再取得に失敗しても成功済みキャッシュは消去せず、取得日時は元のまま保持します。キャッシュの復元を新しいFTL識別情報の観測とは扱いません。

macOSは機器の情報をIORegistryという一覧に保持しています。NenRingはここから、内蔵SSDのコントローラの「Controller Characteristics」を取得します。NANDのメーカー（`vendor-name`）、世代（`nand-marketing-name`）、ページやブロックの大きさ、ダイの数、`chip-id`、`firmware-version`、`msp-version` などです。

コントローラのクラス名はmacOSのバージョンによって異なります。macOS 26までは `AppleANS3NVMeController`、macOS 27では `AppleANS3CGv2Controller` です。NenRingは次の順に検索します。

`AppleANS3NVMeController` → `AppleANS3CGv2Controller` → `AppleANS2NVMeController` → `AppleANSNVMeController`

### ターミナルでの確認

```bash
ioreg -lrw0 -d2 -c AppleANS3CGv2Controller
```

macOS 26以前ではクラス名を `AppleANS3NVMeController` にしてください。

> **出力を共有するときの注意**：出力の全文には `controller-unique-id`（そのSSD固有のID）が含まれることがあります。Issueなどに全文を貼らないでください。データを提供する場合は、識別子を除いた[診断レポート](DIAGNOSTIC_REPORTS.md)（設定 →「一般」→「アプリ」→「診断レポート」）を使用してください。NenRing自身は `controller-unique-id` を読み込みません。

## Direct FTL（FTLの統計）

取得先は選択したディスクからIORegistryの親をたどって対応付けます。FTLとNAND情報の両方を同じ対象に固定し、最初に検出されたコントローラを採用することはしません。APFSの合成ディスクは物理SSDとして数えず、複数のnamespaceがある場合や長期的な識別が曖昧な場合は関連付けを保留します。NANDモジュールの数やMacの機種名から、FTL取得先の数を決めたり値を合算したりすることはしません。詳細は[ディスクと取得先の対応付け](STORAGE_TARGET_BINDING.md)を参照してください。

### FTLとは

SSDの中では、FTL（Flash Translation Layer）という仕組みが、書き込みをNANDのどこに置くかを管理しています。FTLはNANDに実際に書き込んだ量や、ブロックの書き換え回数（P/E）を記録しています。NenRingはここから、SMARTのみでは判明しない次の値を取得します。

- NANDへの書込量（SMARTはHostからの書込量のみ）
- TLCとpSLC（キャッシュ）それぞれの平均・最小・最大P/Eと、上限のP/E（EOL）
- TLCとpSLCの領域の大きさ（topology）

### 呼び出し方

AppleのNVMe SMARTプラグインはsmartctlも使用している公開のインターフェースです。plugin UUID は `AA0FA6F9-C2D6-457F-B10B-59A13253292F`、interface UUID は `CCD1DB19-FD9A-4DAF-BF95-12454B230AB6` です。この関数表（vtable）のうち、公開されている構造の外側に、Appleが診断（sysdiagnose）で使用する関数があります。

| 種類 | 関数表の位置 | 中身 |
|---|---|---|
| `all` | 0x108 | FTLの統計の全体。NenRingが予測に使用するのはこちら |
| `perm` | 0x110 | 一部の統計。形式は未確認で、研究用の手動取得のみ |

同梱のprobe（`asp-ftl-stats-probe`）は、次の手順で取得します。

1. 「NVMe SMART Capable」の属性を持つ機器のうち、Appleの内蔵NVMeコントローラ（`AppleANS2NVMeController` とその派生クラス）の下にあるもののみを選択します。他社製のNVMeは開きません。
2. その機器のSMARTプラグインを開き、`all`（0x108）の関数を呼び出します。
3. 返ってきたデータ（最大1 MiB）を、そのまま保存します。

probeはアプリとは別のプロセスとして時間制限付きで動作します。起動前に、アプリが所定の場所にあることとコード署名を確認します（[PROBE_SIGNATURE.md](PROBE_SIGNATURE.md)）。

### データの形式と使用しているkey

`all` のデータは、「key・個数・値」の並びです。各レコードは、リトルエンディアンの64ビット値で始まります。下位32ビットがkey、上位32ビットが続く値の個数で、そのあとに64ビットの値が個数分続きます。この形はAppleの公開仕様ではなくmacOS 26（25G83）で解析したものです。

予測に使用する主なkeyは次のとおりです。

| key | 意味 | 形 |
|---|---|---|
| 4 | Host書込量 | 値1つ（4 KiB単位の暫定値） |
| 18 | NAND書込量 | 値1つ（4 KiB単位の暫定値） |
| 34 | 稼働時間 | 値1つ |
| 124・503・125 | 最小・平均・最大のP/E | 値2つ（TLC、pSLC） |
| 943・942 | TLC・pSLCの上限P/E（EOL） | 値1つ |
| 49・50・129 | ページの大きさ、TLC・pSLCのブロックあたりのページ数 | 値1つ |
| 52・85・86 | 仮想ブロックの総数、pSLC（Intermediate）領域とTLC（User）領域の開始位置 | 値1つ |

TLCとpSLCの領域の大きさは、ブロックの数 × ブロックあたりのページ数 × ページの大きさで計算します。参照機（256 GB）では、TLCが642ブロック（約258.5 GB）、pSLCが79ブロック（約10.6 GB）です。

### 値を信じる条件

非公開のインターフェースであるため、次の確認を重ねています。

- **毎回のSMART照合**：同device・24時間以内のSMARTとのHost書込量差が1%または5 GBの大きい方の範囲内かを確認します。有限で正の上限P/E、平均P/Eと最大P/Eの関係も確認します。NAND書込量は、単位の取り違えのみを検出する広い幅で確認します。Host書込量の半分未満の場合と、容量×平均P/Eが1 TB以上あるときにその0.5〜2倍の外にある場合は失敗とします（参照機ではNAND/Hostが約1.59、容量×平均P/Eとの比が約1.01）。前回の比較資料がある場合、Power On Hours差の変化も、2時間＋取得時刻差の許容内かを確認します。失敗した取得は保存せず、自動取得を停止します。Host照合の資料不足と、比較先のSMARTが2分より古いときの不一致では保存のみ保留し、POH資料不足は補助比較待ちとします。
- **補助照合と残差**：Controller／SMART損耗率、pSLC損耗率とP/E比を、Researchの取得値と原データ・Residualに表示します。定義や丸めの違いのみでは保存を停止しません。既存D7・生涯／区間残差と内部活動のraw増分も併記します。詳細は[DIRECT_FTL_CROSS_VALIDATION.md](DIRECT_FTL_CROSS_VALIDATION.md)にまとめています。これらは全private keyの意味や保持性能の保証ではありません。
- **自動取得の条件**
  - Apple Siliconの内蔵Apple SSDのみを対象にします。確認済みのmacOS（26・27）に加え、14・15でも互換性を仮定してFTL `all`の自動取得を試みます。14・15のABIやkey意味は確認済みにしません。
  - その他のmacOSでは、手動取得がSMART照合を通過した場合に、そのMacのそのメジャーバージョンで自動取得を開始します。14・15でも照合成功後は「このMacでSMARTと照合済み」と記録しますが、全keyの意味を検証したとは扱いません。対応するすべての機種で確認したわけではありません。
  - 自動取得の失敗後も設定した間隔を待ち、3回連続で失敗した場合は停止します。照合不一致は直ちに停止し、ローカル照合記録を取り消します。手動のみの保存設定を上書きせず、自動で管理者取得やsysdiagnoseを起動しません。
- **境界の確認**：macOSやファームウェアの更新をまたぐときは、更新の前後で値が連続しているかを確認します（[INSTRUMENT_BOUNDARY_CONTINUITY.md](INSTRUMENT_BOUNDARY_CONTINUITY.md)）。counterの連続性は研究用keyの意味や保持性能を検証するものではありません。

### ターミナルでの確認

FTLの統計を取得する標準のコマンドはありません。アプリに同梱しているprobeを、直接実行することはできます。

```bash
/Applications/NenRing.app/Contents/Resources/ASPProbes/asp-ftl-stats-probe --kind all
```

確認済みでないmacOSでは `--allow-unreviewed-build` を付けない限り動作しません。`--output-dir` に、他のユーザーが書き込めないフォルダを指定すると、取得したデータを保存します。

> **注意**：これはアプリと同じ、Appleの非公開インターフェースの呼び出しです。読み取りのみですが、Appleはこのインターフェースをサポートしておらず、macOSの更新により変更されることがあります。確認していないmacOSでの実行は、自己責任で行ってください。手動probeの結果は、自動監視や予測への採用が成功したことの証明にはなりません。

## snapshot probe（研究用）

`asp-snapshot-probe` は、コントローラの別の入口（ユーザークライアントのselector 9）から、診断用のsnapshotを取得する研究用のprobeです。header（0x91）と本体（0x16）の2種類があり、どちらも中身の形式はまだ確認していません。設定画面から手動で実行する場合のみ使用し、寿命予測には使用しません。コントローラは `AppleANS2NVMeController` とその派生クラスで検索し、macOS 27の `AppleANS3CGv2Controller` でもheaderを取得できることを確認しています。

以前あったtunnel probe（0x106・0x129・0x12b）は削除しました。常に管理者権限が必要で、多くは失敗していたためです。

## asptoolのログ（任意）

Appleの `asptool` が出力する `asptool_snapshot.log`（sysdiagnoseに含まれます）を、研究用に読み込めます。NenRingが `asptool` やsysdiagnoseを実行することはありません。

- **読み込み**：「設定 → 研究」の「asptoolログの照合」で、ログ、sysdiagnoseの `.tar.gz`、または展開したフォルダを選択します。アーカイブからは `ASPSnapshots/asptool_snapshot.log` と、取得元の確認に使う `sw_vers.txt`・`SystemProfiler/SPNVMeDataType.spx` のみを取り出します。ログは `~/Library/Caches/io.github.mugisk.NenRing/asptool-imports/` に保存し、同じ場所の `-asptool_source.json` に、macOS build・macOSのバージョン・内蔵SSDのモデルとファームウェア・ログの出力時刻を保存します。SSDのシリアル番号は保存しません。アーカイブ自体は変更しません。展開は180秒で打ち切り、取り出したファイルが512 MiBを超えた場合も中止します。展開中は「中止」で止められます。途中まで展開したファイルは、いずれの場合も削除します。sysdiagnoseのアーカイブ全体にはシステムログ・プロセスの一覧・ネットワークの状態なども含まれるため、共有しないでください。
- **sysdiagnoseの作成**：「ターミナルで実行…」を押すと、ターミナルで `sudo sysdiagnose` を開始します。パスワード（設定によってはTouch ID）の入力と確認はターミナルで行い、NenRingはパスワードを扱いません。完了するとFinderに出力ファイルが表示されます。NenRingは `/private/var/tmp` に新しいアーカイブが作成され、書き込みが終わったことを確認してから自動で読み込みます。待機は30分で終了し、その後は「最新のsysdiagnoseから読み込む」で読み込めます。
- **利用方法**：ログと同時刻のDirect FTL取得があれば、その値を直接比較します。前後2点の間隔が48時間以内で、同じdevice・keyの対応表・firmware・単位、累積counterとP/Eが逆行せず、両方が現在の連続性laneに採用されている場合のみ、Host・NAND書込量と稼働時間を補間して比較します。片側しかない場合は、24時間以内で連続性laneに採用された取得と比較します。系列変更・逆行・取得間隔超過では比較を保留し、P/EとEOLも比較値として出しません。結果はResearchの「生データ」に表示します。
- **判定**：比較した値が次の基準をすべて満たす場合に「基準内で一致」とします。Host・NAND書込量の差は±0.1%以内、Power On Hoursの差は±1時間以内、TLC・pSLCの平均P/Eは前後のDirect FTLの値の範囲内、EOLは完全一致です。前後のDirect FTL取得がなく、30分以内の取得もない場合や、比較値・Direct FTLのmacOS build・ファームウェアが欠けている場合は「判定できません」とします。
- **時刻の根拠**：アーカイブから取り出したログはアーカイブに記録された出力時刻（asptoolがログを書き出した時刻）を使用します。この時刻はアーカイブのコピーや移動では変わりません。ログ単体を読み込んだ場合はファイルの更新日時を使用します。更新日時はコピーで変わることがあるため、前後のDirect FTL取得の間にある場合のみ判定します。
- **取得元**：数値の判定とは別に、ログと同じsysdiagnoseの `sw_vers.txt` と `SPNVMeDataType.spx` から、macOSのメジャーバージョンとSSDファームウェアの系列（先頭の数字。591と591.40.3は同じ系列）がDirect FTLと一致するかを確認し、「一致」「未確認」「不一致」と表示します。ログ単体や展開したフォルダを読み込んだ場合と、これらのファイルがない場合は「未確認」です。不一致の場合は「判定できません」とします。
- **照合時のFTL取得**：読み込んだログの時刻が現在から30分以内の場合は、照合の前にDirect FTLを1回取得します。この取得は手動取得と同じ扱いで、SMARTとの照合に合格した場合のみ保存します。
- **確認済みの環境の記録**：数値が基準内で一致し、取得元も一致した環境を、macOSのメジャーバージョンとファームウェアの系列（例：macOS 27・591）ごとに、このMacで確認済みの環境として記録し、設定に表示します。各記録には最後に確認したmacOS build・ファームウェア・ログの日付を表示します。取得元が未確認の場合は記録しません。診断レポートにも含めますが、含めるのはmacOS build・macOSのバージョン・firmware・ログの日付のみで、ログの内容は含めません。取得元が一致したログで不一致になった場合は、その記録を取り消します。記録は設定から個別に削除でき、削除した記録は、同じログで同じ判定が出ても再び追加しません。記録はアプリの環境設定に保存し、計測履歴のファイルには書き込みません。記録は表示のためのもので、Direct FTLの自動取得の可否、検証済み実行buildの一覧、寿命予測には影響しません。
- **読み込み上限**：1行1 MiB、ファイル全体512 MiBです。長い行・過大ファイルは理由を示して読み込みを中止します。原本は変更しません。
- **予測には使用しない**：読み込んだログは寿命予測・WAF・損耗の系列に含めません。以前のバージョンが読み込んだasptoolのデータも同じ扱いです。

## 取得から予測まで

1. **保存**：取得した値は `~/Library/Application Support/NenRing/` に保存します。
   - `history.jsonl`：SMART
   - `temperature-history.jsonl`：温度と、同時に読んだ読み込み・書き込みバイト数
   - `asptool-snapshots.jsonl`：FTL
   - `usage-settings.json`：使用設定
   - `ASPDirectProbes/`：probeの取得物（定期取得で成功したものは解析後に削除し、失敗したものは確認のために残す）
   - `history.lossless/`、`temperature-history.lossless/`、`asptool-snapshots.lossless/`：確定済みの観測ブロックと、その一覧
   - `archive/`：旧バージョンで間引いた記録の保管庫（新形式への移行時に復元する）

   読み取れない行があった場合は、破棄せずに別のファイル（`*.rejected-*.jsonl`）に退避します。読み取れない行が読み取れる行より多い場合は、ファイルを書き換えず、元のまま `*.unreadable-<UTC日時>.jsonl` に名前を変更して残し、読み取れた行のみで新しいファイルを開始します。新しい形式のファイルを古いバージョンが開いた場合などに、履歴の大部分がbase64の退避ファイルへ移動することを防ぐためです。

   **履歴の可逆集約**：SMART・温度・FTLの観測は最大256件ずつまとめ、共通する値を一度のみ保存して圧縮します。ID・時刻・変化した値はすべて残し、統計には元の観測列を渡します。保存のために古い観測を日次や平均値へ置き換える処理は行いません。グラフ描画用の点数削減は別に行います。

   - `.jsonl` は直近の追記用です。確定済みの記録は `.lossless/` に移動します。バックアップでは `.jsonl` のみではなく `.lossless/` を含むディレクトリ全体を対象にしてください。
   - 圧縮ブロックは読み戻して全観測との一致を確認し、SHA256を記録します。通常の追記で過去の全履歴を書き換えません。
   - 初回移行前のJSONLを `*.pre-lossless-v1.jsonl` に残します。旧 `archive/` の記録も復元し、元の保管庫は変更しません。温度の旧日別summaryは元の観測を復元できた場合に解析入力から除外します。
   - 旧バージョンのアプリは新形式を読み取れるとは限りません。復元手順と形式・負荷の説明は[計測履歴の可逆集約](LOSSLESS_HISTORY_STORAGE.md)を参照してください。
2. **連続性の確認**：macOSやファームウェアの更新、取得経路の変更をまたいで、同じ計測器として扱えるかを確認します。
3. **書込増幅（WAF）**：FTLのNAND書込量 ÷ Host書込量です。全期間の値と、直近の値を組み合わせて予測に使用します。
4. **寿命予測**：TLCとpSLCそれぞれの残りのP/Eを、Host書込量に換算します。先に尽きる方で寿命を決め、保存履歴全体の書込ペースで年数に換算します（[NAND_MODEL_V2_4.md](NAND_MODEL_V2_4.md)）。

FTLを取得できない場合は、SMARTのPercentage UsedとHost書込量、または参考TBWから暫定の推定を出します（[REFERENCE_TBW.md](REFERENCE_TBW.md)）。

## アプリが行わないこと

- 統計取得時のSSD設定の変更、ファームウェアの操作（履歴と設定の保存は別です）
- 任意の関数やopcodeの総当たり
- ユーザーの許可なく、測定値やシリアル番号等を送信すること
- 利用者の操作なしに、管理者認証を求めること

これらの確認を通過しても、非公開インターフェースからの取得、推定したtopology、暫定の単位、他機種への転用に関する研究上の制限は残ります。
