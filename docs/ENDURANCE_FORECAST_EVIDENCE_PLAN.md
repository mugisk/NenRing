# 寿命予測の根拠とダッシュボードの分担

ダッシュボードの根拠表示を改善したときの、実装上の判断を記録したものです。SMARTやFTLの生の履歴は変更しません。また、研究用の診断を信頼性の保証として扱うこともしません。

## ペースにもとづく到達日

各予測行は元々保持している残Host書込量の予算をそのまま使用します。この同じ残量から、独立した2つの日付を算出します。

```text
直近ペースでの到達日 = 現在 + 残Hostバイト ÷ currentWorkloadBytesPerDay
保存履歴ペースでの到達日 = 現在 + 残Hostバイト ÷ recordedHistoryBytesPerDay
使用開始ペースでの到達日 = 現在 + 残Hostバイト ÷ lifetimeBytesPerDay（使用開始日がある場合）
```

- **直近のペース**：`WriteRateSummary.currentWorkloadBytesPerDay` を使用します。30日、7日、90日の順に試行し、最後は全期間の値で代用します。「寿命」画面の比較に表示します。
- **保存履歴のペース**：`WriteRateSummary.recordedHistoryBytesPerDay` を使用します。ダッシュボード、メニューバー、「寿命」画面の到達時期に使用します。
  - 保存済みの連続履歴から算出します。
  - 「保存履歴」と表示し、観測した期間も示します。短い保存期間をデバイスの全期間のように表示することはしません。
- **使用開始からのペース**：`lifetimeBytesPerDay` を使用します。使用開始日がある場合のみ、SMARTの累積Host書込量を使用開始日からの経過日数で割って算出します。計測前の使用状況を含む平均のため、現在の使用状況と異なる場合があります。
  - 保存履歴の観測が7日未満の間のみ、ダッシュボード、メニューバー、研究用の推計の到達時期に暫定で使用します（`forecastPaceBytesPerDay`）。7日以降は保存履歴のペースに切り替えます。
  - 「寿命」画面では比較列としていつでも確認できます。
- ペースがない、有限でない、または0の場合は到達日を算出しません。残りの予算が0の場合は、既に到達しています。
- 残Hostバイトは最後に予測へ入力したFTLの時点の値です。到達日を算出する際は、その時点から最新のSMARTまでに増加したHost書込量を残量から差し引いてから、今日を起点に換算します。FTLの時点のSMARTは前後1日以内の値から補間します。補間できない場合は残量をそのまま使用します。表に表示する合計と残量はFTLの時点のままのため、「現在＋残量＝合計」の関係は変化しません。
- 自動取得の設定で、Direct FTLを2日を超えて取得できていない場合は、入力日時を「古い予測」と表示します。取得間隔は最長1時間のため、2日間取得できていなければ取得が停止していると判断します。境界の確認待ちで予測の入力のみが古い場合は、取得自体は継続しているため表示しません。

これらの日付はシナリオで、寿命の予算そのものを変えるものではありません。以前の正規化した50/35/15の経路は、`NANDEnduranceV2` からも中央のダッシュボードからも削除しました。現在と長期の日付はどちらも `EndurancePaceForecast` で直接計算します。

## 予測WAFの根拠の扱い

中央の寿命予測はRetention Researchの「事前に見込むHost量」の設定を流用しなくなりました。直近のWAFの重みは `ForecastWAFEstimator` が保持します。

```text
q_forecast = 観測したHostバイト ÷ (観測したHostバイト + 予測用に事前に見込むHostバイト)

予測WAF = exp((1-q) ln(全期間のFTL WAF) + q ln(直近のFTL WAF))
```

予測の根拠の尺度は既定で1 TBのままですが、独立した任意の設定 `forecastWAFPriorEquivalentHostBytes` で表します。`retentionDailyWAFPriorHostBytes` を変更すると、Retention Researchの診断は変化することがありますが、中央の寿命予測は変化してはなりません。取得の回数は、qの入力にはなりません。

## 累積Hostの扱い

Hostの値には2つの役割を明確に分けて持たせています。

```text
WAF用のHost   = FTLのNANDカウンタと組になるFTLのHostカウンタ
累積Host       = 条件を満たす場合に、照合したSMARTのData Units Written
```

SMARTの累積値を使用するのは、次の条件をすべて満たす場合のみです。

- 同じデバイスのスナップショットである。
- 受け入れた連続性レーンのFTLスナップショットから±24時間以内である。
- 判明しているファームウェアの識別と矛盾しない。
- FTLのHostカウンタとの差が10%以内である。

満たさない場合、中央の総Host予測はFTLのHost値に切り替え、その根拠を暫定として示します。新しいSMARTの値を、最新であるという理由のみで、境界より前の古いFTLの状態と組み合わせることはしません。

## WAFの期間と、ファイルシステムの空き容量

7日・30日・90日のWAFの計算はDirect FTLの連続性、リセット、単位、学習除外のルールをそのまま使用します。受け入れたHost/NANDの差分の区間ごとに、その時間の範囲を記録します。そのうえで、その区間の中で取得した同じデバイスのSMART `DriveSnapshot` の値を探します。

- 各WAFの期間は照合できたSMARTのサンプル数と、観測したファイルシステムの空き容量の最小値を持ちます。容量が判明している場合は、空きの割合も持ちます。バイト数しかないサンプルも、そのバイト値は使用します。
- ダッシュボードではこれを小さく「空き最小」として表示します。
- これはAPFS（ファイルシステム）の空き容量で、NANDの予備領域や、推定した物理NANDの使用量ではありません。
- WAFの区間と重なるSMARTのサンプルがない場合は「履歴なし」と表示します。現在の空き容量で代用したり、欠けた時間を補間で埋めたりはしません。
- 空き容量が少ないという観測は参考情報で、WAFやTBWを自動で補正しません。

## バンドカウンタの増分による検証

キー349/350の累積値によるチェックは、従来どおりです。条件は、スナップショットが3つ以上、2つの累積カウンタとP/Eの比がどちらも0.95〜1.05、ばらつきが1%以内であることです。

これとは別に、増分の比によるチェックをTLCとpSLCで分けて計算します。

- 確認済みのデバイスでは平均P/Eが整数刻みなので、両方の領域が同じ隣り合うスナップショットの組で進むことは求めません。
- 途切れのない同じtopologyの区間ごとに、その領域のP/Eが上がったスナップショットを記録し、最初の上昇から最後の上昇までで比を測定します。

```text
TLCの増分比  = Δ userBandsProgrammed ÷ (TLCのバンド数 × Δ TLCの平均P/E)
pSLCの増分比 = Δ intermediateBandsProgrammed ÷ (pSLCのバンド数 × Δ pSLCの平均P/E)
```

- TLCとpSLCは、それぞれの上昇の境界、カウンタ、バンド数、連続性のチェックを使用します。区間の中でP/Eが横ばいになるのは問題ありません。
- 次の場合は区間を分けます。比はこれらの境界をまたいで計算しません。
  - カウンタやP/Eのリセット・減少。
  - データの欠け。
  - 重複または逆転したタイムスタンプ。
  - geometryの変化。
  - 研究セッションの区間。
  - 更新直後の一時的な変化による学習除外。
- 区間を集計に入れるのは、最初から最後の上昇の境界までで、P/Eが3以上進んでいる場合のみです。それより短いものは診断値として表示できますが、カウンタの検証には使用できません。
- 条件を満たす区間はバンドの書込回数の合計と、期待されるバンドの書込回数の合計でまとめられます。
- 増分による経路を受け入れるのは、各領域が独立に条件を満たす区間を持ち、その集計の比が0.95〜1.05に入る場合のみです。
- 経過日数や隣り合うサンプルの間隔の数は、領域ごとに示す根拠で、合否の閾値ではありません。これは、整数のP/Eが1段上がるのに数日かかる一方で取得は数時間おきに行っている、という状況に対応するためです。サンプルの多さを、損耗の根拠が多いことと取り違えないようにしています。

研究用の診断ではTLCとpSLCの比、P/Eの進み、経過日数、サンプル間隔を分けて表示します。テストでは次を確認しています。

- 6時間おきのスナップショットで整数のP/Eが保たれ、約3日に1段上がる場合。
- 領域ごとに独立して進む場合。
- 除外の境界。
- 単調には増えるが尺度が間違っているカウンタを退けること。

これは研究用の意味のチェックで、物理容量の検証や、NAND書込量の独立した測定ではありません。受け入れた場合は、既存のバンド経路の残差診断が使用可能になります。カウンタは中央のNAND予算、WAFの予測、自動の倍率には入りません。単調に増えても意味が異なるカウンタは、比のテストで不合格になるはずです。

## ダッシュボードの分担

- 使用されていなかった `LegacyDashboardView` の入口を削除しました。その後、旧ダッシュボード（`DashboardView.swift` の `LifePredictionPanel` など）と、画面から開始できなくなっていた軽量研究の実行も削除しました。保存済みの研究sessionは履歴と率学習の除外のために引き続き読み込みます。
- スリープと復帰、ログイン項目、取得の予定の調整は、`DashboardModel+Scheduling.swift` にまとめています。公開するUIの状態は引き続き `DashboardModel` が保持します。
- 履歴の走査と、信頼性イベントの記録の読み書きは、`DashboardAnalyticsCoordinator` に委ねています。モデルは生成の順番を管理し、最後に完了した分析結果のみを公開します。
- これらはモジュール内部の分担で、公開APIの変更ではありません。取得の間隔、生データの保存、モデルの入力は変更されません。

## 検証で確認する事項

テストでは次を確認しています。

- 2つのペースによる予測と、ペースが無効な場合の振る舞い。
- デバイスとWAFの区間による、SMARTの空き容量の照合。
- 空き容量の履歴がない場合。
- 数日の短い系列からの、増分比の受け入れ。
- 単調には増えるが尺度が間違っているカウンタを退けること。

既存の累積値の検証と残差のテストは、回帰のテストとして残しています。
