# 他環境の診断レポート

[English](DIAGNOSTIC_REPORTS.en.md) · [文書の目次](README.md)

別のMac・容量・macOSでの取得状況を確認するために、診断レポートを提供する手順と、保守側での確認方法を説明します。レポートの提出のために負荷試験やsysdiagnoseを実行する必要はありません。

## 利用者の手順

1. 通常のSMART取得を行います。smartmontoolsが必要です。
2. 「設定 → 一般 → アプリ → 診断レポート → 提供する…」を開きます。英語UIではSettings → General → Application → Diagnostic report → Share…です。
3. 開いた画面の「保存…」でJSONを保存します。ファイル名は `nenring-report-<UTCの日付>-<機種ID>.json` です。
4. 内容を確認し、共有したくない使用量や構成情報を削除します。
5. 「GitHubでIssueを開く」で、Diagnostic reportテンプレートのIssueを開きます。タイトルには機種ID・容量・macOSのbuildが入ります。「Diagnostic report」の欄へファイルをドラッグし、必須の共有確認（Sharing review）にチェックを入れて投稿します。公開リポジトリのIssueでは添付内容も公開されるため、共有に同意できる範囲のみを送信してください。

アプリが開くのはIssueの作成ページのみで、ファイルを送信することはありません。

Direct FTLを取得できていなくても報告できます。未取得の値を0で補完しないでください。取得に失敗した場合は、画面の状態と再現操作を記載してください。報告のために管理者認証を繰り返さないでください。

## 共有範囲

schemaVersion 3のレポートは、機種・CPU・OS build、アプリのバージョン、SSDモデル・firmware・論理容量、`smartctl` のバージョンと終了状態、SMART使用カウンタ、温度、取得済みNAND構成、FTL要約、観測した計測器の組み合わせ、asptoolログとの照合で確認済みの環境（macOS build・macOSのバージョン・firmware・ログの日付）を含みます。日時はUTC日単位です。確認済みの環境は「設定 → 研究」で削除でき、削除した記録はレポートに含めません。schemaVersion 2との違いは確認済みの環境の項目の追加のみです。

FTL要約には現在選択中のSMARTデバイスとIDが一致する履歴のみを使用します。対象が不明な履歴や、SMART未取得時のFTL履歴は含めません。元の履歴は削除しません。

レポートにはシリアル番号、device ID、デバイスパスを含めず、アプリが自動で送信することもありません。ただし、機種・構成・使用量の組み合わせは個体を推測する材料になり得ます。「完全匿名」とは表現しません。raw JSON、probeバイナリ、sysdiagnose全体やログを追加で添付しないでください。

asptoolログとの照合で確認済みの環境としてレポートに含めるのは、macOS build・macOSのバージョン・firmware・ログの日付の4項目のみです。`asptool_snapshot.log` の内容は含めません。このログには、書込量・P/E・不良ブロック・RAID復旧の統計・書込キャッシュのヒストグラム・異常終了後の起動時間など、SSD内部のカウンタが数千行記録されており、使用状況の詳しい履歴に当たります。Issueへ添付する必要はありません。ほかの用途で共有する場合は、内容を確認したうえで判断してください。sysdiagnoseのアーカイブ全体にはシステムログ・プロセスの一覧・ネットワークの状態なども含まれるため、共有しないでください。NenRingがアーカイブから抽出するのは `asptool_snapshot.log` の1ファイルのみです。

## 保守側の確認

- アプリのrevisionとschemaを確認し、未知のschemaを現行のものとみなしません。
- Apple内蔵SSDか外付けかを区別します。外付けSMARTに内蔵SSDのFTLを関連付けません。
- 実行build、対応表のbuild、provenance、firmware、controller、geometry、単位状態を別々に確認します。
- SMARTとFTLの累積値は、取得時刻が異なります。完全一致を要求せず、既存の照合・境界検査の根拠を確認します。
- 単一レポートは取得例であり、長期連続性・P/E進行・保持性能を検証した証拠ではありません。
- 未知hardwareや形式は未確認のまま記録し、報告数のみでkeyの対応表を確認済みへ昇格させません。
- 投稿者への追加依頼は必要な最小項目に限定し、負荷試験・未知opcode走査・sysdiagnoseを標準の報告手順にしません。

内部の処理は `DiagnosticReportBuilder`、互換性と個人を識別できる情報の除外の検査は `DiagnosticReportTests` を参照してください。

テストでは、SMART・FTLのないレポートが欠測のまま生成されることと、選択した外付けデバイスとは別IDの内蔵FTL履歴が出力へ混ざらないことも確認します。デバイスIDは照合に使用するのみで、レポートへ出力しません。これは模擬入力の検証であり、別機種で実取得が成功することの保証ではありません。
